结论先行

v0.3 应开发一个 local deterministic Evaluation Harness：用固定任务集驱动 agent run，读取 JSONL trace，执行 deterministic checks，输出机器可读 JSON 和自包含静态 HTML 技术审查报告。第一版不做线上服务、排行榜、LLM judge、live provider ranking、context engineering、memory、delegation、sandbox 或 MCP。

这个选择直接回答路线图问题：behavior regressions 能否被度量？ v0.3 不解决“哪个模型更强”，也不扩展 agent 平台能力；它只让本项目在后续修改 agent loop、tool registry、permission、provider 或 context 策略前，有一套本地、可复现、可审查的回归信号。

本轮要开发什么

产品目标

建立本地 eval harness，能运行固定 fixture tasks，并判断 read-only inspection、patch approval、policy denial、trace completeness 是否回归。

用户入口

建议命令形态：bun run eval -- --suite v0.3 --out .agent-harness/evals/latest。

核心产物

report.json 是机器契约；自包含 report.html 是 reviewer-facing 技术审查视图；Markdown 可作为 fallback。

成功标准

固定任务、required checks、trace parse、safety denial 和 report completeness 都有可复现指标和真实运行结果。

技术选型

推荐架构

  1. EvalTask 固定任务定义，覆盖 inspection、patch、safety、trace。
  2. TaskRunner 复制 fixture 或创建临时 git repo，运行 deterministic provider。
  3. TraceScorer 读取 JSONL trace，执行 deterministic checks。
  4. ReportDataModel 汇总 totals、metrics、task results、limitations、sources。
  5. JSON report 作为机器契约，HTML report 作为自包含审查视图。

拒绝方案

  • 不使用 LLM judge 作为 P0，因为不可复现且会让回归信号变弱。
  • 不接入 SWE-Bench 作为 P0，因为规模和依赖会遮蔽本项目 trace scoring 的第一性问题。
  • 不做 hosted dashboard，因为 v0.3 只需要本地 release evidence。
  • 不做 leaderboard，因为它会把目标从回归检测变成模型排名。

产物 用途 稳定性 约束
report.json 测试、CI、脚本和后续自动化消费。 最高，作为机器契约。 schema version 必须显式；字段缺失用 null 或 not_run，不得猜测。
report.html 人类审查、失败定位、证据浏览、release handoff。 中等，必须从同一 JSON 数据模型渲染。 单文件、自包含、无网络资源；不重新计算 pass/fail；所有内容 HTML escaping。
report.md 文本 fallback 或贴入 PR / release note 的摘要材料。 中等。 不能替代 JSON 契约；长证据浏览能力弱于 HTML。

为什么选择自包含静态 HTML

  • 它能表达长表格、失败折叠、状态过滤、证据跳转，比 Markdown 更适合 reviewer 快速定位问题。
  • 它不需要 dev server，不引入前端构建链，不扩大成 dashboard。
  • 它可以和 JSON 使用同一数据模型，保证“人看到的结果”和“机器验收的结果”一致。
  • 它可以被 browser smoke 验证：非空、窄 viewport 无明显重叠、过滤/折叠控件可用、无外部资源。
  • 它适合 release evidence，但不能作为唯一契约；机器契约仍必须是 JSON。

Benchmark 问题与指标

Benchmark question Metric 阈值 说明
固定任务能否发现 behavior regression？ task_pass_rate, required_check_pass_rate 100% P0 suite 必须全绿；失败时报告 task id、check id 和 evidence。
trace 是否足够支撑 scoring？ trace_parse_rate, required event coverage 100% JSONL parse error 和缺失 event 必须是确定性失败。
safety regression 是否可定位？ safety_denial_rate, unexpected_write_count 100% denial, 0 writes unsafe command / unsafe patch 不得写入，且要记录 policy error。
HTML 是否支持 release review？ html_review_smoke, report_privacy pass 浏览器验收与隐私扫描必须覆盖自包含 HTML。

Implementation stories 建议

  1. Task schema and fixture matrix：定义 EvalTask schema，锁定 4 个 P0 tasks：inspection、patch approval、patch denial、command denial。
  2. Trace parser and checks：实现 JSONL parser、required event checks、final answer grounding、worktree checks、permission checks。
  3. Runner：实现 eval suite runner，隔离 worktree，调用 deterministic provider 和 real tool registry。
  4. Report data model：统一 totals、metrics、task results、limitations、sources，先生成 JSON。
  5. Static HTML renderer：从 report data model 生成自包含 HTML，包含 summary、task matrix、failed checks、sources、decisions、benchmark metrics。
  6. Browser and privacy gates：检查 HTML 无外部资源、核心交互可用、无本机绝对路径、用户目录或 token-looking secret。

风险与缓解

风险 影响 缓解
HTML 和 JSON 结果不一致 reviewer 被错误视图误导。 HTML 只渲染 JSON 数据模型，不重新计算 pass/fail。
trace 事件字段漂移 scorer 误判或漏判 regression。 schemaVersion、required event tests、parse error 带行号。
fixture 被污染 eval 结果不可复现。 mutable tasks 复制到 output worktree，源 fixture 只读。
报告泄露本机路径或 secret release evidence 不可分享。 report privacy scan 覆盖 JSON、Markdown、HTML。
scope 漂移到平台化 eval v0.3 无法按故事交付。 LLM judge、leaderboard、hosted service、external benchmarks 全部 later 或 reject。

最终技术建议

v0.3 的正确技术路线是：先交付一个小而硬的 deterministic regression harness。它要复用本项目已有优势：scripts/smoke.ts 的 deterministic provider、runAgentTask、real tool registry、permission gate、JSONL event logger 和 patch safety tests。HTML report 只作为本地审查视图存在，和 JSON report 共享同一数据模型。

进入实现前，应先确认 story 1 的 task schema 和 P0 fixture matrix。后续每个 story 都应先写 tests，再实现，并把未运行的 E2E、benchmark 或 browser smoke 明确标为 not_run。
